# ImpactScore V2 design

Status: design, being implemented (GOU-1882, GOU-1880, GOU-1879). Owner: CTO. Tracking: GOU-1878, under the
ImpactScore improvement programme GOU-1864 (audit of 2026-11-08).

This page turns the owner decisions of 2026-11-08 into a data contract, the
computation, the exclusion rule, the display contract, the switch, the
simulation and the tests. Current V1 computation:
[ImpactScore_Computation.md](../ImpactScore_Computation.md).

## Owner decisions (not reopened here)

1. **EPREL filter:** lifted per vertical, with a `minRealWeightCoverage`
   threshold. Below it a product has no ImpactScore and is listed as "Not
   rated". Brand and model stay required.
2. **Weights:** redistributed over the criteria actually filled in. No mean
   imputation in the final score.
3. **`DATA_QUALITY`:** out of the sum. It becomes the confidence indicator and
   no longer counts brand scores.
4. **Display:** score /20, position in the category, real criteria over total,
   computation date, methodology version. Labels computed from the position.
5. **Built dark:** each vertical carries its methodology version in
   `ImpactScoreConfig`. V2 is published only after a V1/V2 simulation and the
   owner's approval.

**Guiding rule:** while a vertical's `methodologyVersion` is 1, nothing
observable changes (scores, exclusions, listings, sitemap, display). A single
switch per vertical moves it to V2; setting it back to 1 restores V1 at the
next batch.

Values still unknown (thresholds, label bounds, robust bounds, verticals where
the EPREL filter is lifted) come from the threshold approval (GOU-1877). Code
reads them from configuration; none is hard-coded.

## 1. Model

### 1.1 Assessment metadata: `Product.impactScoreMeta` (new)

A "Not rated" product has **no** `scores.ECOSCORE` (decision 1). The display
still needs "x of y criteria", the date and the version for it. These fields
therefore cannot live on the ECOSCORE `Score`: they go on a product-level
object, written for **every product the batch assesses**, rated or not. The
ECOSCORE `Score` stays the score itself, with no new field.

Class `model/.../product/ImpactScoreMeta`:

| Field | Type | Meaning |
|---|---|---|
| `methodologyVersion` | `Integer` | Methodology applied (1 or 2). Missing = legacy score, treated as version 1 |
| `methodologyRevision` | `String` | Short fingerprint (SHA-256, 8 hex) of the active matrix, computed at load time like `promptRevision`. Feeds the version history (lot 4) |
| `scoredAt` | `long` (epoch ms) | Instant of the batch that assessed the product (same convention as `lastChange`) |
| `status` | `String` (`RATED`, `NOT_RATED`) | Outcome |
| `notRatedReason` | `String` | `LOW_COVERAGE` (C below threshold), `NO_REAL_CRITERIA` (C = 0); null when rated |
| `realWeightCoverage` | `Double` 0-1 | C, see 2.2 |
| `realCriteriaCount` | `Integer` | Criteria of the active matrix actually filled in |
| `totalCriteriaCount` | `Integer` | Criteria with weight > 0 in the active matrix |

Rules:

- Written by the batch for each product of the scored cohort (`offersCount >
  0`, not excluded), **in V1 too** (version 1, date, coverage of the V1
  matrix, for information). V1 scores do not change; production gets a
  measure of C and of the date before any switch.
- Cleared together with the scores for excluded or unmatched products
  (`clearObsoleteScores`).
- A product without offers keeps it, like its value of score, but loses its ranks (`ranking`, `scores.*.ranking`), which belong to an earlier cohort (GOU-2071).

### 1.2 `ImpactScoreConfig`: active version and `v2` block

V1 and V2 matrices must coexist (simulation, rollback). The V1 matrix stays
where it is, frozen. V2 is a `v2` block of the same file; `methodologyVersion`
selects the active block.

```yaml
# verticals/src/main/resources/verticals/impactscores/tv.yml
methodologyVersion: 1          # active version; 2 = V2. The only key the switch changes
criteriasPonderation:          # V1 matrix, frozen
  ...
v2:
  criteriasPonderation:        # sums to 1, no DATA_QUALITY, no ECOSCORE
    REPAIRABILITY_INDEX: 0.16
    ...
  minRealWeightCoverage: 0.5   # value from GOU-1877
  eprelRequired: true          # false only where GOU-1877 lifts the filter
  minRatedForPositionLabel: 100  # no label below this rated cohort (default 100)
  positionLabels:              # best first; values from GOU-1877
    - level: excellent
      minBetterThan: 0.90
    - level: good
      minBetterThan: 0.50
    - level: fair
      minBetterThan: 0.10
    - level: poor
      minBetterThan: 0.0
  criteriaScoring:             # per-criterion overrides, V2 only (robust bounds, 2.6)
    POWER_CONSUMPTION_SDR:
      normalization:
        method: MINMAX_QUANTILE
        params: { quantileLow: 0.02, quantileHigh: 0.98 }
```

Accessors on `ImpactScoreConfig` (all code goes through them; no direct
`getCriteriasPonderation()` call outside loading):

- `effectiveMethodologyVersion()`: environment override (5.2), else
  `methodologyVersion`, else 1;
- `activeCriteriasPonderation()`: V1 matrix or `v2.criteriasPonderation`;
- `isEprelRequired()`: `true` in V1, `v2.eprelRequired` in V2 (default
  `true`). The filter cannot be lifted without V2, and going back to V1
  restores it;
- `minRealWeightCoverage()`, `positionLabels()`, `criteriaScoring(key)`;
- `minRatedForPositionLabel()` (`null` in V1) and `positionLevel(betterThan, ratedCount)`, the label rule of 2.4.

Current matrix readers to move to `activeCriteriasPonderation()`:
`EcoScoreAggregationService`, `AbstractScoreAggregationService`,
`ParticipatingScoreHelper`, `VerticalConfig` (`ecoscorePercentOf`,
`getEcoscoreCriteriasSum`, `ecoScoreDetails`), front-api
`CategoryMappingService.mapImpactScoreConfig`. `VerticalsGenerationService`
(AI generation) stays on V1.

Validation (`VerticalYamlValidationTest`, and at load time for the override):

- `methodologyVersion` in {1, 2};
- a `v2` block, when present, is complete: matrix sums to 1 (± 1e-6), no
  `DATA_QUALITY` and no `ECOSCORE`, existing `asScore` criteria;
  `0 < minRealWeightCoverage <= 1`; `minRatedForPositionLabel >= 1` when set;
  `positionLabels` thresholds strictly decreasing, the last one 0;
- `methodologyVersion: 2` requires a `v2` block.

### 1.3 Elasticsearch mapping

The root is `strict`, so the property is explicit, indexed and aggregatable
(lot 3, read-only ES connection):

```json
"impactScoreMeta": { "properties": {
  "methodologyVersion": { "type": "integer" },
  "methodologyRevision": { "type": "keyword" },
  "scoredAt": { "type": "date", "format": "date_optional_time||epoch_millis" },
  "status": { "type": "keyword" },
  "notRatedReason": { "type": "keyword" },
  "realWeightCoverage": { "type": "float" },
  "realCriteriaCount": { "type": "integer" },
  "totalCriteriaCount": { "type": "integer" }
} }
```

Compatible addition through `putMapping` at api startup, no reindex. **Risk:**
with a `strict` root, a document carrying the field before the mapping is
applied is rejected. The PR therefore documents the deploy order (api first)
and checks the `ProductIndexMappingRunner` log and `GET _mapping` on beta, then
production, before the first batch. See
[product-index-mapping.md](../operations/product-index-mapping.md).

## 2. Computation (V2 only, `effectiveMethodologyVersion() == 2`)

### 2.1 No imputation

In V2, `AbstractScoreAggregationService.done()` creates no `virtual` scores
(criteria and brand scores), and `EcoScoreAggregationService` creates no
virtual ECOSCORE. A missing criterion is **absent** from the product.

- Why remove them instead of keeping them for display: a stored virtual score
  carries a mean value that the radar and other readers already draw as a
  real value. "Not filled in" is derived from the criterion's absence against
  the active matrix (4.3).
- V1 is unchanged, virtual scores included.

### 2.2 Coverage C and score

For a product and the active matrix `w` (weights > 0, normalised to Σ = 1):

- a **real** criterion: score present, `virtual != true`, readable relative
  value (`resolveRelativeValue` not null);
- `C = Σ w_i (real criteria) / Σ w_i (all criteria)`;
- `realCriteriaCount` = number of real criteria; `totalCriteriaCount` = number
  of criteria with weight > 0;
- `C == 0`: `NOT_RATED` / `NO_REAL_CRITERIA`;
- `C < minRealWeightCoverage` (compared within 1e-9; the threshold is
  inclusive, `C >= threshold` is rated): `NOT_RATED` / `LOW_COVERAGE`;
- otherwise `RATED`, `score = 4 × Σ_real (w_i × rel_i) / Σ_real w_i` (0-20,
  weights redistributed pro rata over real criteria); `absolute.value = value
  = score` and `relativ.value = score / 4`, as today.

A `NOT_RATED` product has no `scores.ECOSCORE` and a fresh `EcoScoreRanking`,
but keeps its real sub-scores and its `impactScoreMeta`.

### 2.3 `DATA_QUALITY`

Out of the sum in V2 (absent from `v2.criteriasPonderation`, rejected by
validation). It is still computed, as the confidence indicator. In V2 it
counts only real scores of `asScore` criteria listed in
`availableImpactScoreCriterias`, without `BRAND_*`, itself or composites.
Normalisation is unchanged (`MINMAX_OBSERVED` within the category), so the lot
0 badge (`isDataQualityBelowCategoryAverage`) keeps its meaning. V1 unchanged.

### 2.4 Ranking

Over the `RATED` products of the cohort only (unrated products have no
ECOSCORE):

- `count` = `globalCount` = number of rated products;
- in V2, ties share a rank (fixes the unstable order of ties):
  `scores.ECOSCORE.ranking` = number of rated products strictly worse;
  `globalPosition` = 1 + number of rated products strictly better;
- displayed position: `betterThan = ranking / (count - 1)` (lot 0 formula);
  label = first `positionLabels` entry with `minBetterThan <= betterThan`.
  With `count == 1`: no percentage and no label.
- no label when `count < minRatedForPositionLabel` (100 by default, gate 2
  of GOU-1877): the score, the position and the percentage stay. Applied at
  read time by the front-api (`ProductMappingService`, through
  `ImpactScoreConfig.positionLevel`), where `level` is computed from the
  stored ranking: the label is never stored, so the rule follows the cohort
  of the last batch without recomputation (GOU-2137).

### 2.5 Composites and out-of-batch recomputation

- `ParticipatingScoresAggregationService` (DURABILITY, REPARABILITY...) in
  V2: same redistribution over real sub-scores, no threshold; the composite is
  absent when none is real.
- `recomputeFromStoredSubScores` stays limited to the lot 0 V1 defect
  (composite ECOSCORE). In V2 a product without offers is **not** recomputed:
  when its `impactScoreMeta.methodologyVersion` is not the current version it
  shows as "Not rated" (decision 5, 4.2). It is not deleted from the index, so
  rollback stays complete.
- `POST /score/{vertical}` follows the same rules (same aggregator).

Implementation (GOU-1879): sections 2.1, 2.2, 2.4 and 2.5 apply when
`ImpactScoreConfig.isV2Active()`. `AbstractScoreAggregationService.done()`
skips virtual scores; `EcoScoreAggregationService` computes C and the score
from one `Coverage` (criteria weighted above 0), compares C with the threshold
within 1e-9 and treats a missing `minRealWeightCoverage` as no threshold
(only `NO_REAL_CRITERIA`). A not rated product loses any `ECOSCORE` and gets a
new `EcoScoreRanking`. `globalBetter` is the lowest strictly better product;
`globalBest` the best product, ties broken by GTIN. `BatchService.clearObsoleteScores`
does not recompute composite ImpactScores in V2 and
`recomputeFromStoredSubScores` returns null. `POST /score/{vertical}` scores
and reindexes only products with offers that are not excluded in V2.

### 2.6 Robust bounds

Per-criterion override in `v2.criteriaScoring`, merged over the attribute's
`scoring` block, read by a single resolver `effectiveScoring(key, vConf)` that
both `relativizeScoreValue` and `incrementCardinality` use (so that the value
frequencies `MINMAX_QUANTILE` needs are tracked). Strategy: the existing
`MINMAX_QUANTILE`, quantiles of the real cohort, clamped by `scaleAndClamp`
(out-of-bounds values get 0 or 5 depending on `impactBetterIs`). No new
mechanism.

Delivered (GOU-1883): `effectiveScoring` (`AbstractScoreAggregationService`) replaces the attribute's
`normalization` block (method and params; scale, transform and policies stay the attribute's) by
`v2.criteriaScoring.<key>.normalization` in V2 only; V1 never reads the override. Values of gate 2
(GOU-1877, applied by GOU-2137), following the measures of `lot1b-distribution-2026-11.md` section 6.2:

- `MINMAX_QUANTILE` 0.02 / 0.98: `tv` `POWER_CONSUMPTION_SDR` and `_HDR`, `oven`
  `OVEN_ENERGY_CONSUMPTION_CYCLE`, `dishwasher` `WATER_CONSUMPTION` and `ENERGY_CONSUMPTION_100_CYCLES`,
  `washing-machine` `WATER_CONSUMPTION` and `ENERGY_CONSUMPTION_100_CYCLES`;
- `MINMAX_FIXED` 0 to 1 W: `POWER_CONSUMPTION_OFF` (`tv`, `dishwasher`, `washing-machine`) and
  `POWER_CONSUMPTION_STANDBY` (`dishwasher`); 0 to 2 W: `tv` `POWER_CONSUMPTION_STANDBY_NETWORKD` (its 98th
  percentile equals its median, so a quantile range would be degenerate);
- air conditioners: no override (13 and 2 real values).

### 2.7 Derived criteria: "repairability or durability" (GOU-2041)

The French durability index replaced the repairability index (TV on
2025-01-08, washing machines on 2025-04-08): a product holds one or the other.
Two criteria, one always missing, would lower every product's C. The V2
matrices of `tv` and `washing-machine` therefore weight a single derived
criterion, `REPAIRABILITY_OR_DURABILITY_INDEX`, with the former weight of
`REPAIRABILITY_INDEX`:

| Vertical | V2 weight | V1 |
|---|---|---|
| `tv` | 0.1609195 | `REPAIRABILITY_INDEX` 0.14, unchanged |
| `washing-machine` | 0.1363636 | `REPAIRABILITY_INDEX` 0.12, unchanged |

- **Mechanism.** An attribute declaring `scoreSources` (ordered keys) is a
  derived score: `Attribute2ScoreAggregationService` never reads its own
  value, takes the raw value of the first source holding a parseable value
  (`DURABILITY_INDEX`, else `REPAIRABILITY_INDEX`, never an average), and
  records it in `scores.<key>.metadatas.source`. Without a parseable source the
  criterion is absent and its weight is redistributed (2.2). It is computed
  only while the active matrix weights it, so V1 products never hold it.
- **Scale.** Its own `MINMAX_FIXED` 0-10 to 0-5: 7/10 gives 3.5 from either
  source. `REPAIRABILITY_INDEX` keeps `MINMAX_OBSERVED` for V1.
- **Label.** `scoreTitle` "Indice de réparabilité ou de durabilité (note
  officielle sur 10)", read by the methodology page and "Why this score?".
- **Composites.** In V2, `ParticipatingScoreHelper` treats a derived criterion
  as available through its sources and skips a participating attribute the V2
  matrix does not weight: `REPARABILITY` uses the derived criterion instead of
  `REPAIRABILITY_INDEX`. V1 is unchanged.
- **Validation.** `ImpactScoreMethodology` refuses a derived V2 criterion
  reading an unknown or derived source, or weighted next to one of its
  sources. `availableImpactScoreCriterias` is unchanged, so `DATA_QUALITY` is
  unchanged in V1 and V2.

## 3. Exclusion

- `updateExcludeStatus` adds `missing_eprel` only when
  `vConf.getImpactScoreConfig().isEprelRequired()`. `missing_brand`,
  `missing_model`, `missing_attr_*` unchanged. A product without a vertical
  uses the default configuration, so the filter stays.
- The rule moves into a pure function (`ExclusionRules.evaluate(product,
  vConf)`) called by `updateExcludeStatus` and by the simulation.
- **Re-evaluation of excluded products:** automatic at the first 13:00 batch
  after the switch, which reruns `updateExcludeStatus` on every product of the
  vertical. No bulk operation outside the batch. Back in V1, they are excluded
  again at the next batch and `clearObsoleteScores` clears their scores.

| Place | Effect of a product that is no longer excluded |
|---|---|
| Listings and search (`SearchService`, `excluded=false`, `offersCount > 0`) | Listed |
| Sort by ImpactScore (`scores.ECOSCORE.value`) | An unrated product has no value and sorts last (ES default `_last`); covered by a test |
| "Top X %" filters and `impact_*` subsets | The painless script skips documents without `ranking`, so unrated products are not included |
| Sitemap (`exportVerticalForSitemap`) | With a recent offer: present, rated or not. Without: present only with a current-version score (4.2) |
| "Rated products" counter (GOU-436) | Counts `exists scores.ECOSCORE.value`: rated products only. Unchanged |

## 4. Front-api and frontend

### 4.1 DTO contract

`ProductScoresDto` gains `impactScore` (`ProductImpactScoreStatusDto`), always
set for a product of a vertical:

| Field | Source |
|---|---|
| `status` | `RATED` or `NOT_RATED`, after the display rule (4.2) |
| `notRatedReason` | `LOW_COVERAGE`, `NO_REAL_CRITERIA`, `OUTDATED_METHOD` (score of another version), `NOT_SCORED` (never assessed) |
| `methodologyVersion`, `methodologyRevision`, `scoredAt` | `impactScoreMeta` (`scoredAt` in the product DTO date format) |
| `currentMethodologyVersion` | the vertical's effective version |
| `realWeightCoverage`, `realCriteriaCount`, `totalCriteriaCount` | `impactScoreMeta` |
| `position`, `ratedCount`, `betterThanPercent` | `EcoScoreRanking` and `scores.ECOSCORE` |
| `level` | label computed from the position (2.4); **null in V1** and below `minRatedForPositionLabel` rated products |

`ImpactScoreConfigDto` (category) gains `methodologyVersion`,
`minRealWeightCoverage` and `positionLabels`; its `criteriasPonderation`
becomes the active matrix, so the vertical's methodology page shows V2 after
the switch. The OpenAPI client is regenerated as `front-api/AGENTS.md`
describes.

### 4.2 "Current version only" rule

Applied **in the front-api** (`ProductMappingService.mapScores`), once for
every client:

- a product's effective version = `impactScoreMeta.methodologyVersion`, or 1
  when missing (legacy score);
- shown when the product's effective version equals the vertical's current
  version; otherwise `scores.ECOSCORE`, `ecoscore` and `ranking` are not
  exposed and `impactScore.status = NOT_RATED` (`OUTDATED_METHOD`);
- in V1 a score without version is still shown, so nothing changes before the
  switch. In V2 a score without version (a product without offers never
  rescored) is "Not rated", as decided. After a rollback to V1, a V2 score is
  "Not rated" the same way.

Implementation (GOU-1882): the rule also covers `base.ecoscoreValue` and the
score in the product meta description (`ProductSeoMetaService`), through
`ImpactScoreConfig.isCurrentMethodology` and
`Product.impactScoreMethodologyVersion()`. In version 1 the scores output is
unchanged; only `impactScore` is added. `betterThanPercent` uses the lot 0
formula (`scores.ECOSCORE.ranking / (globalCount - 1)`), `position` and
`ratedCount` come from `EcoScoreRanking`.

The same rule applies to queries, so the sitemap keeps no "Not rated" product
on the strength of its score. `exportVerticalForSitemap(vertical,
currentVersion)` replaces `exists scores.ECOSCORE.value` with:

- version 1: `exists value` AND (no `impactScoreMeta.methodologyVersion` OR
  it equals 1);
- version 2 or more: `exists value` AND `impactScoreMeta.methodologyVersion`
  equals the version.

Sitemap effect to measure **before the switch** (simulation, section 6):
products not excluded, without a recent offer, with an ECOSCORE, per vertical.
They leave the sitemap at the switch and come back as soon as they have an
offer and go through the batch.

### 4.3 Display (V2 only; V1 rendering unchanged)

The frontend uses `impactScore` only when `currentMethodologyVersion >= 2`:

- rated: "14,2/20 - better ranked than 97 % of rated TVs - 11 of 13 criteria
  filled in - computed on 8 Nov - method v2", label from `level`;
- not rated: "Not rated", no gauge, with the reason ("Not enough verifiable
  data to rate this product (x of y criteria)"; "Being recomputed with
  method v2" for `OUTDATED_METHOD` and `NOT_SCORED`);
- criteria of the active matrix missing on the product: "not filled in" row,
  never drawn at the mean in the radar;
- reliability badge: `DATA_QUALITY` (2.3), consistent with the criteria count;
- labels and wording behind configuration (`positionLabels`, i18n) until the
  legal analysis (GOU-1886) is done.

## 5. Switch

### 5.1 Production

Per vertical, a configuration PR in this repository: `methodologyVersion: 2`
in `impactscores/<vertical>.yml` (the `v2` block is already merged with the
approved values). Approved by the owner (gate 3, GOU-1888), then a normal
release: the configuration is on the classpath, so the switch ships with a
release.

### 5.2 Environment override (beta pilot vertical, fast rollback)

Property `impactscore.methodology-version-overrides` (for example `tv:2`), read
by `VerticalsConfigService` at load time and rendered from a GitHub
Environment variable (`IMPACTSCORE_METHODOLOGY_OVERRIDES`) **for api,
front-api and ui together** (batch, display and sitemap must see the same
version). Uses:

- beta: pilot vertical in V2 without touching production (GOU-1888);
- production: rollback without a release (`tv:1`), by Ops, then the next
  batch.

Empty by default. A value outside {1, 2}, or V2 without a `v2` block, fails
startup.

Implementation (GOU-1882): rendered by `scripts/deploy/render-service-secrets.sh`
as the config tree file `impactscore.methodology-version-overrides` of api, ui
and front-api (comma-separated `<vertical>:<version>` pairs). An empty GitHub
variable is not rendered and keeps the previous render, so `none` clears an
override; an unknown vertical also fails startup. An invalid `v2` block that is
not active only logs a warning at startup; `VerticalYamlValidationTest` refuses
it. See [prod-service-secrets.md](../operations/prod-service-secrets.md).

### 5.3 Rollback

Set the vertical back to V1 (PR or override), next batch: EPREL filter
restored, products that entered are excluded and cleared, V1 scores, V2
scores of products without offers hidden. Nothing deleted in V2 prevents this.

## 6. Simulation (V1 against V2, no production write)

**Data.** `_source` export of the products of the verticals concerned, read
only. The read-only ES connection (500 documents per call, 1 MB, output in the
model context) does not suit a full export, so Ops produces it with
`ops_readonly`, in the backup format (`<vertical>.jsonl.gz`, one `Product` JSON
per line), after the first production batch of lot 0. It is stored outside
the git repository, in the build host's `~paperclip`. Integrity check through
the ES connection: product count per vertical and per `excludedCauses`.

**Harness.** A test class of the `api` module, skipped in CI
(`@EnabledIfSystemProperty(named = "impactscore.simulation.input")`), reusing
the bootstrap of `ImpactScoreRealVerticalsTest` (real configurations, real
aggregator in production order):

1. load the export (`SerialisationService.fromJson`);
2. **V1:** cohort `offersCount > 0 && !excluded` (stored exclusion),
   configuration forced to version 1;
3. **V2:** exclusion recomputed by `ExclusionRules.evaluate` with the
   candidate `eprelRequired`, same cohort rule, configuration forced to
   version 2; candidate parameters (threshold, labels, bounds) read from a
   `-Dimpactscore.simulation.params` file to compare several GOU-1877 values;
4. brand scores: a stub `BrandService` returns the `BRAND_*` scores read from
   the export;
5. **fidelity check:** offline V1 against the stored ECOSCORE; at least 99 %
   of the products of the last batch within 0.05, otherwise the simulation is
   invalid and the gap is investigated before any conclusion.

**Outputs, per vertical:** counts (rated V1, rated V2, not rated by reason,
entering products); p5/p50/p95 distribution and split per label; V1/V2
Spearman; top 20 V1 against V2; the 20 largest rank changes explained per
criterion; products added to listings and to the sitemap, and products
leaving them (4.2); audit cases (27" E/G TV, smartphones with imputed
repairability, air conditioners). Report
`docs/impactscore/v2-simulation-<date>.md` with CSV of the changes; the export
is never committed.

## 7. Tests

`ImpactScoreRealVerticalsTest`, extended to V2 on the 7 real configurations,
production order, version forced to 2 (configured threshold, or 0.5 until it

1. **No imputation:** no `virtual` score; the score equals `4 × Σ_real w·rel /

3. **Exact C:** `realWeightCoverage` = sum of real weights; right counts;

4. **Ranking:** `count` = number of rated products; best `ranking = count - 1`

5. **`DATA_QUALITY` out of the sum:** changing it does not change the score;
   absent from every V2 matrix; count without `BRAND_*`.
6. **V1 unchanged:** in version 1, scores identical to those before the change
   (snapshot) and current assertions green.
